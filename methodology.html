Methodology

Evaluation protocol

A model receives a task specification and, where supplied, CAD geometry. It submits a Python program that constructs the mesh, runs a simulation and writes the requested values and evidence. The evaluator replays the program offline and checks the outputs against held-out references.

CAD

The shape

A 3D model of a part, like the file an engineer sends to a 3D printer or a machine shop. We use the STEP format, which any CAD program can open.

FEM

The simulation

The finite element method cuts the shape into thousands of tiny pieces (a mesh) and solves the physics on every piece. It is how engineers check a part before anyone builds it.

Reference

The trusted answer

Each task has an answer the model never sees. It comes with the real CAD design, collected from the web (open engineering projects, CAD datasets and solver test suites), or is computed by us and checked on three meshes.

The single-shot protocol permits one model call and one submitted program per task. Exploratory independent trials are reported separately and never pooled into pass@1. Agentic runs with tools or feedback must also be reported separately.

Grading

Four checks, scored separately

Getting a number right is not enough on its own. A model could guess or copy a known answer, so the files behind the number are checked too.

1 · Numbers

Right answer

Every requested value is a real number inside its pass band. Bands are usually 5 % or 10 %; values read off a published colour plot get 20 %.

2 · Files

Real work

The program, the exported shape, the mesh, the result fields, the solver log, a refinement record and the software versions must all be there.

Shape

Right part

When the model builds the CAD itself, an automatic check compares it with ours: same number of solids, volume within 2 %, surfaces within 0.5 mm. Expert human annotators then verify its features, regions and the faces used for supports and loads.

4 · Review

Honest setup

Expert human annotators, who do not know which model wrote the code, verify the CAD and sign off the supports, loads, mesh and convergence against the file hashes.

A task passes only when the numbers are right and the expert human annotators sign off. Results are reported separately for tasks that give the CAD and tasks that need the model to build it, and runs with tools or feedback are reported apart from single-shot runs.

Like dense-reward benchmarks, we also report partial credit: the numerical score is the fraction of a task's values inside their bands (0, ½ or 1 for a two-value task), so near-misses are visible, not just pass or fail.

Dataset construction

Where the tasks and answers come from

Tasks are built from real CAD designs and their FEM results collected from the web, plus a family of generated buckling tasks. Every task is checked before it is admitted.

Sources

Collected from the web

  • Open CAD datasets: GE jet-engine bracket designs (SimJEB), AgentFEM brackets, GeoPINONet holed plates, CADWorld.
  • Open engineering projects: a 3D-printable cycloidal gearbox, a rigging plate, morphing-wing test plates.
  • Solver test suites: Code_Aster validation tests, the fcVM FreeCAD workbench, FeenoX, NAFEMS benchmarks, Wolfram FEM tests.
  • Generated: 82 buckling traps (100 built, 18 held back).

Answers

One trusted answer per value

  • Main set (135 values): 85 from the source's results tables, 24 from its result files, 12 exact formulas, 5 read from stress plots, 4 from the source's own checker, 4 from another solver, 1 from the source's model.
  • Buckling traps: computed by us with quadratic elements and an eigen-solver that cannot skip modes, on three meshes, with a closed-form check where one exists.
  • No answer is ever shown to the model.

Validation

Checked before admission

  • 17 of the 64 main-set answers reproduced with an independent FEM model; the worked example adds one more.
  • Buckling traps admitted only if three meshes agree and the trap holds: 18 of 100 were held back (10 differed from the closed-form value by more than 3 %, and 8 perforated strips did not pass admission).
  • Six task defects found during model runs (a wrong prompt detail, a reference from a simpler model, a drawing never attached) are marked and not counted against any model.
  • Difficulty labels (easy or hard) will be set from the mean score once three or more models are run.

Experiments

Harness, models and metrics

Harness

One program, one replay

  • Single shot: one model call per task returns main.py; no tools, no feedback. On the leaderboard: medium reasoning effort and at most 20 000 output tokens.
  • Agentic (reported separately): the model may run code and read errors, then submits once; at most 250 tool calls, 45 minutes of command time and 180 minutes per task.
  • Every submission is replayed once by sandbox_runner.py: offline, read-only inputs, 600 s, 8 GiB (6 GB on the leaderboard), 2 threads, with CadQuery, Gmsh, NumPy/SciPy, meshio, scikit-fem and CalculiX 2.23.

Evaluation scope

What has been run

Leaderboard (11 November 2026): ten models, single shot, on 100 tasks: the 64-task main set and 36 buckling traps. One attempt per task, so these are numerical pass@1.

Qwen3-235B-A22B: all 64 main-set tasks, one agentic submission each (numerical pass@1, main set).

GPT-6 Astra failure study: single-shot trials on 86 tasks chosen to expose failure modes. Some tasks were tried more than once, so those counts are not pass@1.

Metrics

What we report

  • Pass@1: share of tasks with every value in band and the expert review signed off.
  • Numerical pass@1: share with every value in band.
  • Numerical score: mean share of values in band (partial credit).
  • Family-averaged pass rate, cost and tokens per task, and failure type (no answer, wrong value, refused), which does not depend on any band.
